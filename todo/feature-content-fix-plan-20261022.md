### 補抽內部核對邊界（不逐項加入功能介紹）

- 「不在場重抽」入口目前只在有效名額抽滿時顯示；釋出後名額不足，入口會消失，不能承諾隨時都能再開選人視窗。
- 一次要釋出多人時，在確認前勾選完整名單；逐一抽出模式後續每次補一位。
- 補抽無可抽者時不能保證補滿；不應提示使用者任意放寬資格或開啟重複中獎來湊名額。
- 已領獎不能直接釋出；不要把「取消領獎狀態」寫成缺席重抽的例行捷徑。
- 同獎項不重複會排除已釋出者；跨獎項仍依其他有效中獎紀錄與設定判定，釋出不等於全場禁抽。
- 已釋出的原兌獎連結不能再兌獎，原紀錄與連續替補關係要保留。

## B：操作保護方案

### B1　錯誤訊息按原因處理

`resources/js/lottery.js:8601–8609` 目前把所有 403 都當成存取碼失效；正式 API 關閉活動也回 403（`LotteryFrontendController.php:267–269`）。

- 讀取錯誤的 message/code，只在 `invalid_operator_token` 清除 operator token 並要求輸入存取碼。
- `lottery_closed` 顯示「活動尚未開放抽獎」並更新狀態；不清除合法存取碼。
- 切換中、正在抽獎、資格不足、伺服器非 JSON 回應分別處理；失敗時不自行再送新的抽獎請求。
- 若請求逾時，提示先核對後台紀錄；不能暗示逾時一定沒有抽出結果。

### B2　讓伺服器確認預期獎項

現況前台只送 `run_id`，服務只抽伺服器目前的 `current_prize_id`。只補「先切回」的文案仍不能完全防止過期畫面操作。

- 前台送出按下抽獎時的 `expected_prize_id`；必要時再帶切換版本／nonce。
- 伺服器在確認活動狀態與目標一致後才抽獎。不一致時回明確的衝突結果、更新畫面，不能抽取另一個獎項。
- 開抽、切獎與預覽切換的互斥方式必須一致，不能只在鎖外讀一次狀態。要重新讀取受保護的活動狀態，避免在比對後又被切換。
- 不能因 UI 忙碌旗標失效或心跳逾時，就當作已保證沒有並行操作。
- 需要一併檢查正式端點、Demo、舊快取前端與 embedded 預覽。若新增必填欄位，安排相容部署／版本更新，避免新版 API 使舊頁面全部抽不了。
- 不要在釋出時自動把目前獎項改回 A，避免干擾正在準備的 B 獎；由明確的切換操作配合伺服器目標驗證。

### B3　領獎與釋出併發：待實測，不列為已重現

`PrizeRedrawService` 會鎖獎項，但 `ClaimController::apiVerify` 是先讀狀態、再更新；`ManageClaims` 的手動標記與掃碼更新也各有路徑。現有順序測試不足以證明兩者同時操作的安全性。

- 所有領獎／釋出路徑採一致的鎖定順序與條件更新；成功結果應互斥，不能同時變成已領獎與已釋出。
- 驗收包含兩位工作人員同時操作、同一 token 連點、舊視窗勾選已改變狀態的紀錄。
- 需使用與正式相同類型資料庫驗證並行交易；記憶體 SQLite 不能代替 MySQL 的鎖定驗收。本輪沒有執行此並行實測。

## C：分析器修復方案

### C1　資格計算共用，資料來源分開

- 抽出純資格運算：固定包含／排除、一般群組、全體員工、活動已中獎、特定獎項已中獎、同獎項重複規則、組織範圍。
- 正式抽獎使用正式資料建立狀態；模擬使用輸入快照與每輪獨立的虛擬得獎狀態。
- **不能只改「包含為空就回空集合」一行。** 分析器目前不展開系統群組；若不一起處理「全體員工」，常見的全員參加設定可能反而全部算成 0。
- 未選包含、空一般群組都應為 0；排除優先；混合指定員工＋系統群組採聯集，且不跨組織。
- 跨獎項排除必須使用本次模擬前面獎項的結果，不能直接讀取線上已中獎群組作為每輪固定名單。
- 舊 `exclude_prize_winners` 規則須盤點是否還有既有活動使用，再決定轉換或拒絕不支援的設定；不能模擬默默支持、正式卻忽略。
- 完整支援前若要先推出小修，對尚未支援的組合明確阻擋並說明原因，不生成看似完整的錯誤報表。

### C2　明確定義模擬起點

建議此版只提供「從活動開始模擬」：每一輪從空的虛擬得獎狀態開始，按獎項順序抽完整名額，不讀取現場得獎者當作當輪結果。

獎項順序、逐一／一次全抽、同獎項重複都需定義。若規則包含在本獎項抽完前也會變動的已中獎群組，不能假設「整獎一次抽」永遠等同多次逐一抽；必須按正式每次操作的資格更新時機模擬。

「依目前進度補完」應另案提供，需完整定義有效／已領獎／已釋出／替補與目前獎項，不能悄悄混進同一份分析。

### C3　送出時保存輸入快照

`RunLotteryAnalysis.php:37,57` 目前在工作執行時重新讀活動及設定，送出排隊到執行之間的修改會影響結果。

- 以送出當下的活動／獎項順序、名額、規則、員工 ID／部門及群組成員建立一致快照，保存算法與快照版本。
- 盡量只保存運算必要資料，不把 Email、電話等無關資料複製進分析快照；快照與下載仍限活動所屬組織授權。
- 報表說明分析起點、規則版本、送出／完成時間與設定摘要。活動名稱事後改變，也不能讓舊報表看起來使用了新設定。
- 排隊後修改名單、群組或獎項，不應改變該 run；重新分析才使用新的快照。重試也使用同一份輸入，結果仍可能因隨機取樣不同，不保證逐位相同。
- 既有報表保留原算法標記，不自動套新指標或默默重算。若新增欄位，使用相容的新增 migration，不修改已發布 migration 來回填新語意。

### C4　中獎統計分清「名額」與「至少中一次的人」

目前 `win_rate = total_wins / eligible_exposures`，允許重複時可以大於 1，不能直接解讀為個人中獎機率。

- 保留名額次數，改以清楚名稱及單位呈現，例如「每可抽人次平均取得名額」；不要用 100% 上限截斷，否則會掩蓋真實名額數。
- 若要提供 0–100% 的模擬比例，需另外統計「該獎項至少中一次的人次／該獎項可抽人次」，每輪先去重。這與原本中獎次數的指標不同，不能直接改同一欄的數值而不標版本。
- 部門可抽占比＝部門可抽人次／全部可抽人次；部門中獎占比＝部門中獎次數／全部中獎次數。占比差異用百分點表示，不是相對成長百分比。
- 同步處理後台表格、Excel 的六個分頁／圖表／PivotData、CSV、公開說明與示例；不是只換公開頁標籤。

### C5　工作與額度驗收

- 1–1,000 次的介面、服務／工作邊界應一致；目前後台有驗證，但服務只有最小值保護，不能只改 input 的 max 就宣稱支援一萬次。
- 定義空名單、0 可抽者、可抽人數小於名額、重複開關、部門留白、任務失敗、重複送出與 worker 重試的結果。
- 結果未完成不可下載；跨組織不可讀取／下載；分析不得寫正式 `PrizeWinner`、通知、釋出或廣播正式中獎事件。
- 在實際部署條件量測後，再決定是否增加到 10,000 次，包含耗時、記憶體、工作逾時、進度更新與失敗復原。
